# Стратегия тестирования

Основа — [конспект книги Владимира Хорикова «Принципы юнит-тестирования»](https://github.com/alexey-goloburdin/knowledge-base/blob/main/Книга%20«Принципы%20юнит-тестирования»,%20Хориков%20Владимир.md).
Проверяем единицы поведения через публичные операции, а не устройство классов.
Сценарии независимы, ожидаемые значения заданы явно, ошибки проверяются вместе
с отсутствием нежелательных изменений. Моков репозитория/DbContext нет.
Процент покрытия и число тестов не являются критерием готовности.

## Что защищаем

| Область | Риск | Проверка |
| --- | --- | --- |
| Domain | Принятие некорректных данных или частичное обновление | Пустые ID/имена, неизвестные enum до/после допустимого диапазона, недопустимые URL; после отказа сохраняются прежние характеристики |
| Domain | Неверная публикация образа | Пустой состав; переходы 2 → 1 и 1 → 0; удаление отсутствующей вещи |
| Domain | Нарушение владения/дублирование | Чужая вещь; две разные вещи с одинаковым ID |
| Application | Несанкционированные изменения | Матрица команд чужого пользователя; пустой actor; состояние и ссылки после отказа |
| Application | Ошибка разграничения доступа | Публичные и приватные ссылки независимы; приватные вещи видны только в контексте опубликованного/расшаренного образа; неизвестные токены ничего не открывают |
| Application | Чрезмерный или неполный отзыв доступа | Удаление вещи из всех образов, опустевшие и ещё заполненные образы, несколько ссылок, сохранение посторонних ссылок |
| Application | Возвращение ранее отозванного доступа | Заполнение пустого образа не активирует старую ссылку |
| Infrastructure | Потеря данных при материализации | Сохранение и чтение через разные контексты всех сущностей, необязательных полей, enum, состава и исходного токена |
| Infrastructure | Несогласованное состояние | Чтение pending изменений, удаление с очисткой связей, отзыв ссылок, откат при ошибке сохранения |
| Infrastructure / PostgreSQL | Конкурентные команды | Независимые контексты читают до двух сохранений: проверяем оба порядка, конфликт и откат, свежий повтор, отзыв ссылок после заполнения |
| Infrastructure | Повторное полное чтение вещей | Счётчик SQL для публичного, личного, отдельного и shared просмотра; проверяем состав DTO и постоянное число SELECT на операцию |
| Infrastructure | Обход доменных ограничений | Прямые SQL-записи проверяют уникальность токена/состава, общего владельца и запрет удаления владельца с гардеробом; проверяем конкретные коды ошибок БД |
| PostgreSQL | Отличие реального провайдера от SQLite | Применение настоящей миграции, чтение сохранённого гардероба, ограничения, удаление и откат |
| In-memory | Сбой уже начатого чтения при записи | Детерминированное перекрытие чтения и записи без sleeps и стресс-циклов |

SQLite — быстрая реляционная проверка модели, не замена PostgreSQL. Проверка snapshot
работает без сервера; выполнение миграции проверяется только PostgreSQL-тестами.
Все проверки БД читают итоговое состояние через новый контекст там, где проверяется
сохранение. Ошибка ожидается по конкретному типу/коду, а не по любому исключению.

Подтверждение почты проверяется через HTTP с записывающим отправителем вместо SMTP:
запрет входа, одноразовость, срок, повторная выдача, CSRF и ошибки доставки.
Реляционные проверки используют независимые контексты для конфликтов подтверждения/выдачи.
PostgreSQL отдельно проверяет обновление старой схемы с аккаунтом и default для новых записей.
Существующие сценарии cookie проходят подтверждение через тестовый HTTP-helper; в production
обхода подтверждения нет. Реальная доставка SMTP требует ручной проверки с настроенным сервером.

## Запуск

```powershell
dotnet test Outfitly.sln
dotnet test Outfitly.sln --filter "FullyQualifiedName~Domain"
dotnet test Outfitly.sln --filter "FullyQualifiedName~Application"
dotnet test Outfitly.sln --filter "FullyQualifiedName~Infrastructure"
```

Для PostgreSQL задайте `OUTFITLY_TEST_CONNECTION_STRING` через окружение и запустите:

```powershell
dotnet test Outfitly.sln --filter "FullyQualifiedName~PostgreSql"
```

Используйте отдельную тестовую базу. Тесты применяют миграции в собственных схемах
`outfitly_test_<guid>` и удаляют эти схемы после завершения. Общие данные и базу целиком
не удаляют. Требуются права CREATE SCHEMA. Тесты могут выполняться параллельно.
Если соединение не задано, результат — Skip с объяснением. Если соединение задано,
ошибка подключения/миграции считается провалом теста. После аварийного завершения
процесса могут остаться тестовые схемы; удалять их следует отдельно в тестовой базе.

## Проверка качества

При разработке выполнены две точечные мутационные проверки: отключение обработки
пустого состава и отключение проверки владельца. Соответствующие тесты упали
на нарушенном поведении. Исходники после экспериментов восстановлены.
Это проверка двух важных регрессионных гарантий, а не полный mutation score.

Для защиты конкурентных команд выполнена отдельная точечная мутация:
отключение обновления версии образа. Все четыре расписания конкурентного удаления
падают на отсутствии ожидаемого конфликта; после восстановления защита проходит проверки.

Набор относится к существующим правилам Domain/Application и адаптерам хранения.
Тривиальные DTO/getters не проверяем отдельно. API-тесты запускают реальный pipeline
через WebApplicationFactory: JSON-валидация, коды/Location, CRUD между запросами,
чужой владелец, состав образов, публикация, ссылки и удаление. БД изолирована на тест,
тестовая identity доступна только в тестовом проекте. Отдельная проверка production-схемы
подтверждает, что заголовки клиента и произвольные bearer tokens дают 401.
AuthenticationApiTests проверяют настоящую cookie-схему: регистрацию/вход, владение,
CSRF, отзыв и истечение сессий, поддельные cookie, rate limiter и ошибки сохранения.
ApiFactory использует HTTPS; тестовые владельцы тоже получают CSRF-токен через API.
AccountPersistenceTests проверяют пароль и обновление хеша через новый контекст.
PostgreSqlAccountTests применяют миграции и проверяют конкурентную регистрацию,
атомарность создания аккаунта и сохранение/отзыв сессий.
Существующие HTTP-тесты frontend dev server запускаются отдельно через `npm test`.

PhotoApiTests проверяют загрузку, замену, доступ по публикации/ссылке/образу,
CSRF, очистку файлов при неудачном commit и конкурирующей замене. Каждый ApiFactory
использует отдельный временный каталог фото. PhotoConcurrencyTests читают результат
через новый контекст; PostgreSQL-сценарий применяет реальные миграции.
SameOriginApiTests проходят путь frontend → регистрация → cookie → CSRF → загрузка
на одном HTTPS origin через TestServer. CatalogApiTests проверяют HTTP-контракт,
PostgreSqlCatalogTests — кириллицу, буквальные шаблоны поиска и стабильные страницы
на PostgreSQL. ShareLinkListApiTests проверяют повторное получение и отзыв ссылок.

SMTP.BZ проверяется без сети: SmtpEmailTests подменяет транспорт и проверяет
параметры STARTTLS/аутентификации, обе MIME-версии, ссылки, отмену и безопасные ошибки.
PasswordResetApiTests использует записывающий email-сервис; PasswordResetPersistenceTests
проверяет срок, повторную выдачу и гонки с чтением через свежий контекст. Его PostgreSQL
проверка требует отдельной тестовой базы, как остальные PostgreSqlFact.
