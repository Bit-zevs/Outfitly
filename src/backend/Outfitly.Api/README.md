# Базовый HTTP API

API использует PostgreSQL через scoped `WardrobeService`, EF-репозиторий и
`IUnitOfWork`. Каждый успешный запрос изменения сохраняется одним вызовом
`SaveChangesAsync` до отправки ответа. Удаление вещи, изменение всех образов
и отзыв ссылок входят в одну транзакцию. При ошибке сохранения успешный ответ не выдаётся.

## Авторизация

Production использует cookie `__Host-Outfitly.Auth`: HttpOnly, Secure, SameSite=Lax,
Path=/, без Domain. Сессия живёт восемь часов без продления; cookie непостоянная
(без «запомнить меня»). Только HTTPS. При каждом запросе проверяются сессия в БД,
её срок/отзыв и существование аккаунта/пользователя. Выход отзывает текущую сессию;
её скопированная cookie тоже перестаёт работать. Другие сессии продолжают работать.
Повторный вход в этом браузере отзывает его предыдущую сессию.

Identity содержит `ClaimTypes.NameIdentifier` с Guid доменного пользователя.
Application дополнительно проверяет владение ресурсами. Контракт создания вещи/образа
не содержит `OwnerId`; владельца задаёт сервер. Заголовки пользователя и произвольные
bearer tokens не авторизуют запрос. Тестовая схема существует только в тестовом проекте.
API возвращает 401/403 в ProblemDetails без HTML-перенаправлений.

### Аккаунты

| Метод | Маршрут | Запрос и результат |
| --- | --- | --- |
| GET | `/api/auth/csrf` | `{ "token": "…" }`, CSRF-cookie и `Cache-Control: no-store` |
| POST | `/api/auth/register` | `{ "email", "password", "displayName", "username" }` → `201`, пользователь и `confirmationEmailSent`; вход после подтверждения |
| POST | `/api/auth/confirm-email` | `{ "token" }` → `204`; cookie не выдаётся |
| POST | `/api/auth/resend-confirmation` | `{ "email" }` → `202` с общим сообщением для отправленного письма, неизвестного или подтверждённого адреса |
| POST | `/api/auth/login` | `{ "email", "password" }` → `200`, пользователь и auth-cookie |
| POST | `/api/auth/logout` | Без тела, требует входа → `204`, отзыв текущей сессии и удаление cookie |
| PATCH | `/api/auth/me/username` | `{ "username" }`, требует входа и CSRF → `200`, обновлённый пользователь |
| GET | `/api/auth/me` | Требует входа → `200`, пользователь, `Cache-Control: no-store` |

Пользователь в личных ответах: `{ "id", "email", "displayName", "username", "pendingEmail" }`; `pendingEmail` — null без действующего запроса смены адреса. Ответ регистрации не включает `pendingEmail`. Пароли и хеши не возвращаются.
Email обрезается по краям, проверяется на формат и длину до 254 символов; уникальность
без учёта регистра. Имя проверяется доменными правилами. Пароль — 8–128 символов,
без требований к регистру/спецсимволам; пробелы значимы. Дубликат email — `409`,
невалидные данные — `400`, неверный пароль/неизвестный email — одинаковый `401`.
Регистрация, вход, подтверждение и повторная отправка делят лимит 10 запросов за минутное окно на IP без очереди;
превышение — `429`. Остальные маршруты этот лимит не расходуют.

Каждый POST/PUT/PATCH/DELETE под `/api` требует заголовок `X-CSRF-TOKEN` с токеном
из `/api/auth/csrf` и выданную CSRF-cookie. Это касается также регистрации, входа и выхода.
После входа/выхода или смены аккаунта запросите новый токен. Неверный/отсутствующий
токен даёт `400` без выполнения команды; неавторизованный запрос к личному маршруту
по-прежнему даёт `401` до проверки CSRF. GET/HEAD/OPTIONS не требуют токена.

Первая версия рассчитана на один экземпляр API и frontend того же origin.
Восстановление пароля, внешние провайдеры и административные роли не реализованы.

### Подтверждение почты

Новые аккаунты не могут войти до подтверждения: правильный пароль возвращает `403`
с полем ProblemDetails `code: "email_not_confirmed"`, неверный — обычный `401`.
Существовавшие до миграции аккаунты сохраняют доступ. Подтверждение не создаёт сессию.
Письмо ведёт на `/#/confirm-email?token=…`; открытие страницы ничего не меняет,
пользователь нажимает кнопку, frontend отправляет POST с CSRF.

Ссылка действует 24 часа и используется один раз. Неверная, просроченная или использованная
ссылка возвращает `400`, `code: "invalid_confirmation_token"`. Повторная отправка отменяет
старую ссылку; интервал между выдачами — минимум 60 секунд (`429`,
`code: "confirmation_too_frequent"`, `Retry-After: 60`). Конкурентное изменение даёт `409`;
повтор команды требует нового чтения в новом scope.

Письмо отправляется после commit. Если SMTP недоступен при регистрации, ответ остаётся
`201` с `confirmationEmailSent: false`: аккаунт создан, нужно повторить отправку.
При сбое повторной отправки — `503`, `code: "email_delivery_failed"`; новый токен уже сохранён,
поэтому перед следующей попыткой также действует интервал 60 секунд. Автоматических повторов нет.
Настройка SMTP описана в [разработке](../../../docs/development.md#подтверждение-почты-и-smtp).

Отдельных маршрутов для справочника категорий, социальных функций и пользовательских
профилей нет. Фото можно загрузить либо задать внешним URL.

Создание возвращает `201` и `Location`; загрузка фото — `200` с представлением вещи,
остальные успешные команды — `204`.
GET возвращает `200`. Ссылка возвращает `{ "id", "token", "url" }`; `url` относительный,
ведёт к публичному чтению ресурса по токену. `id` используется для отзыва ссылки.
Список ссылок возвращает массив таких же объектов только для активных ссылок;
пустой список — `[]`, чужая цель — `403`, отсутствующая — `404`.
Личные и публичные просмотры вещей/образов не раскрывают токены. В просмотре по
ссылке URL загруженного фото содержит токен этой ссылки. Пустой образ можно сохранить,
но нельзя опубликовать/расшарить. Повторное добавление одной вещи возвращает `409`.

### Тела запросов

Вещь, POST/PUT (name и category обязательны):

```json
{
  "name": "Рубашка",
  "category": "Top",
  "color": "White",
  "size": "M",
  "brand": null,
  "description": null,
  "photoUrl": "https://example.com/shirt.jpg"
}
```

Категории передаются строками: `Top`, `Bottom`, `Dress`, `Outerwear`, `Footwear`, `Accessory`.
Принимается ровно одно имя категории без окружающих пробелов, без учёта регистра.
Списки вроде `Top, Bottom`, числа, числовые строки и отсутствие category — `400`;
опущенные optional поля при PUT очищаются, кроме уже загруженного фото:
отсутствующий/null `photoUrl` сохраняет его. Текущий относительный URL личного фото
можно передать обратно без изменений. Другие внутренние URL назначать запрещено.
Абсолютный API URL считается внутренним только при совпадении origin запроса
(схемы, хоста и порта); внешние HTTP/HTTPS адреса с путём `/api/...` разрешены.
Новый внешний URL заменяет загруженное фото; при существующем внешнем URL null
по-прежнему очищает его. Для удаления загруженного фото используется DELETE `/photo`.

### Загрузка и чтение фото

PUT `/api/items/{id}/photo` принимает `multipart/form-data` с ровно одним файлом
`file`, без дополнительных полей. Требуются cookie владельца и `X-CSRF-TOKEN`.
Поддерживаются `image/jpeg` и `image/png`, до 5 МиБ включительно, максимум 8192 пикселя
по стороне и 25 мегапикселей. Формат проверяется по содержимому и должен соответствовать
MIME (регистр типа MIME не учитывается). Повреждённые, пустые и анимированные файлы отклоняются. Имя файла не используется
как путь; после декодирования сервер учитывает ориентацию и перекодирует фото без
исходных метаданных.

Чтение загруженного фото доступно только в соответствующем контексте: владельцу,
публикации вещи/образа или активной ссылке. Для образа проверяется наличие вещи в составе.
Отзыв ссылки, снятие публикации и удаление членства закрывают соответствующий маршрут.
Анонимные маршруты возвращают `404` при отсутствии доступа или фото; личный — обычные
`401/403/404`. Фото отдаётся с `Cache-Control: no-store` и `X-Content-Type-Options: nosniff`.
Внешние URL сервер не скачивает и не проксирует, их доступом управляет внешний источник.
Уже скачанные клиентом байты отозвать невозможно.

### Поиск и страницы вещей

GET `/api/items` и `/api/wardrobe` возвращают `{ "items": [...], "total": 0, "page": 1, "pageSize": 20 }`.
Это изменение прежнего контракта массива; списки образов остаются массивами.
`total` учитывает фильтры и видимость до пагинации.

| Параметр | Правило |
| --- | --- |
| `search` | Подстрока названия без учёта регистра; `%`, `_` и `\` — буквальные символы |
| `category` | Одно имя категории по тем же правилам, что в JSON |
| `color` | Точное совпадение без учёта регистра |
| `sort` | `nameAsc` по умолчанию или `nameDesc`, затем ID по возрастанию |
| `page` | От 1, по умолчанию 1 |
| `pageSize` | От 1 до 100, по умолчанию 20 |

Фильтры объединяются через AND. Поиск и цвет обрезаются по краям, пустые строки
не ограничивают выборку. Невалидные/повторные известные параметры — `400`;
слишком большое смещение страницы — `400`. Страница за пределами списка возвращает
пустой `items` и действительное `total`. Личный список ограничен владельцем,
публичный — опубликованными вещами. Подсчёт и страница выполняются отдельными запросами:
при конкурентном изменении каталога результаты могут отражать разные моменты времени.

Образ, POST/PUT: `{ "name": "На каждый день", "description": null }`.
Публикация: `{ "isPublic": true }` или `{ "isPublic": false }`; флаг обязателен.
Создание ссылок и изменение состава образа не требуют тела.

Ошибки возвращаются в формате ProblemDetails:
`400` — невалидный JSON/данные; `401` — нет identity; `403` — чужой ресурс или невалидная
identity; `404` — нет ресурса/активной ссылки; `409` — запрещённый переход, дубликат
или конфликт конкурентных команд над образом/фото; `413` — слишком большой файл,
`415` — неподдерживаемый или не соответствующий MIME формат фото. После конкурентного конфликта
перечитайте текущее состояние и повторите всю команду; сохранение откатывается целиком.
Неожиданные ошибки — `500` без внутренних деталей.

## Запуск

Задайте `ConnectionStrings__Outfitly` через окружение или .NET user secrets.
Пример формата без секретов: `Host=localhost;Port=5432;Database=outfitly;Username=outfitly`.
Сначала примените миграции по [инструкции Infrastructure](../Outfitly.Infrastructure/README.md).
API не создаёт БД и не применяет миграции автоматически.

```powershell
dotnet run --project src/backend/Outfitly.Api --launch-profile https
dotnet test Outfitly.sln
```

HTTP-тесты запускают настоящее приложение через WebApplicationFactory и используют
изолированную SQLite БД. Проверяют HTTP-контракт, сохранение между запросами,
авторизацию, валидацию, публикацию/ссылки и согласованное удаление.
PostgreSQL-интеграционные тесты отдельно требуют `OUTFITLY_TEST_CONNECTION_STRING`.

HTTPS, сертификат разработки и хранение ключей описаны в [разработке](../../../docs/development.md).

Текущий синхронный контракт репозитория сохранён для небольшого объёма первой версии.
Асинхронные запросы с фильтрацией в БД и пагинацией — отдельное расширение Application.

## Восстановление пароля

`POST /api/auth/forgot-password` принимает `{ "email": "user@example.com" }`.
Для подтверждённого аккаунта выдаёт одноразовый токен на 1 час; повторная выдача
возможна через 60 секунд и заменяет прежний токен. Ответ всегда `202` с одинаковым
сообщением для неизвестного/неподтверждённого адреса, периода ожидания и сбоя SMTP.
Ошибочный формат email возвращает `400`. Общий лимит account-access может вернуть `429`.

`POST /api/auth/reset-password` принимает `{ "token": "...", "password": "..." }`.
Пароль содержит 8–128 символов. Успех — `204`; недействительный, просроченный или
использованный токен — `400`, code `invalid_password_reset_token`; конфликт — `409`.
Успех погашает токен и делает все прежние сессии недействительными. Cookie входа не
выдаётся: нужно войти с новым паролем. Оба маршрута требуют CSRF и используют общий
лимит account-access. Ссылки письма ведут на `/#/reset-password?token=...` настроенного
frontend origin; GET страницы ничего не меняет. Токен удаляется из текущего маршрута
после успешного сброса.

## Публичные профили и поиск людей

Username содержит 3–30 символов: латинскую букву в начале, далее латинские буквы,
цифры или `_`. Пробелы по краям и один начальный `@` удаляются, регистр приводится
к нижнему. В JSON хранится ник без `@`; отображаемое имя независимо от него.
При регистрации username обязателен. Невалидный ник даёт `400`, занятый — `409`
с `code: "username_taken"`, в том числе при конфликте индекса во время commit.
Повторное сохранение своего текущего ника разрешено. Старый ник освобождается.

| Метод | Маршрут | Результат |
| --- | --- | --- |
| GET | `/api/users?search=anna&page=1&pageSize=20` | `{ items, total, page, pageSize }`; публичные аккаунты по началу ника |
| GET | `/api/users/{username}` | `{ id, displayName, username }` |
| GET | `/api/users/{username}/items?page=1&pageSize=20` | Страница опубликованных вещей пользователя |
| GET | `/api/users/{username}/outfits?page=1&pageSize=20` | Страница опубликованных образов пользователя |
| GET | `/api/users/{username}/items/{id}` | Опубликованная вещь указанного владельца |
| GET | `/api/users/{username}/outfits/{id}` | Опубликованный образ указанного владельца с составом |

Все перечисленные GET доступны без входа. Профиль и поиск включают только подтверждённые
аккаунты и не возвращают email. Поиск принимает `anna` и `@ANNA`, совпадение буквальное
(подчёркивание не является wildcard); точный ник первым, остальные по нику.
Пустой поиск возвращает пустую страницу. `page` ≥ 1, `pageSize` — 1–100; неверные
значения и переполнение смещения дают `400`. Неизвестный профиль, приватный ресурс
или чужой ID под указанным ником дают `404` даже для владельца ресурса.

Публичные карточки вещей и образов содержат `ownerUsername`. Загруженные фото
используют существующие публичные маршруты и проверки доступа. Приватные вещи
опубликованного образа показываются внутри образа, но не появляются в списке вещей.

Frontend формирует `/#/@anna`, `/#/@anna/items/{id}` и `/#/@anna/outfits/{id}`.
Смена ника делает прежние именные ссылки недействительными; перенаправлений нет.
Существующие `/#/public/.../{id}` и `/#/shared/.../{token}` поддерживаются.

## Редактирование аккаунта

| Метод | Маршрут | Тело и результат |
| --- | --- | --- |
| PATCH | `/api/auth/me/profile` | `{ displayName, username }` → `200`, обновлённый пользователь |
| POST | `/api/auth/me/change-password` | `{ currentPassword, newPassword }` → `204`, завершение всех сессий и удаление cookie |
| POST | `/api/auth/me/email-change` | `{ email, currentPassword }` → `202`, `{ pendingEmail, confirmationEmailSent }` |
| DELETE | `/api/auth/me/email-change` | Без тела → `204`, отмена ожидающей смены почты |
| POST | `/api/auth/confirm-email-change` | `{ token }` → `204`, замена адреса и завершение всех сессий изменяемого аккаунта |

Все операции требуют CSRF; `/me/*` дополнительно требуют действующую сессию.
Имя и ник сохраняются атомарно по существующим доменным правилам: при занятом нике
не меняется и имя. Сессия сохраняется. Старый `/me/username` продолжает работать.

Смена пароля и запрос смены почты требуют текущий пароль. Неверный пароль — `400`,
`code: "invalid_current_password"`, без отзыва сессий или изменений. Новый пароль
проверяется по правилам регистрации, повтор пароля проверяет интерфейс. После смены
пароля и подтверждения новой почты требуется повторный вход на всех устройствах;
токены сброса пароля и смены почты погашаются. Восстановление пароля также отменяет
ожидающую смену почты.

Новый email проверяется на формат и уникальность без учёта регистра; текущий адрес
без изменения регистра не считается новым (`400`). До подтверждения работает старый
адрес. Новый адрес не резервируется: уникальность повторно проверяется при подтверждении,
включая уникальный индекс БД. Занятый адрес — `409`, `code: "email_taken"`.

Ссылка смены почты действует 24 часа, используется один раз и не подходит для регистрации
или сброса пароля. Неверная/погашенная/просроченная ссылка — `400`,
`code: "invalid_email_change_token"`. Интервал запросов — 60 секунд, включая после отмены;
ранний повтор — `429`, `code: "confirmation_too_frequent"`, `Retry-After: 60`.
Повторный запрос с текущим паролем заменяет прежнюю ссылку. Отмена удаляет ожидающий
адрес и делает ссылку недействительной. Конфликт параллельных изменений — `409`;
повторять команду следует в новом scope.

Письмо с назначением `EmailChange` отправляется на новый адрес после commit.
Сбой доставки сохраняет `202` с `confirmationEmailSent: false`: запрос сохранён,
пользователь может повторить отправку через минуту. Очереди отправки нет.
Смена пароля, запрос смены почты и подтверждение используют общий лимит `account-access`.

Frontend показывает три независимые формы в аккаунте. Ссылка ведёт на
`/#/confirm-email-change?token=...`; открытие страницы не меняет данные. Подтверждение
выполняется явной кнопкой, после успеха токен удаляется из URL. При подтверждении
из браузера другого аккаунта его сессия не отзывается. Email и pendingEmail
не добавляются в публичные профили и поиск людей.

## Реакции и комментарии

Маршруты относительно `/api/{items|outfits}/{id}`:

| Метод и путь | Назначение |
| --- | --- |
| GET `/engagement` | `views`, `likes`, `comments` (без удалённых), `isLiked`, `canInteract` |
| POST `/views` | Уникальный просмотр; автор не учитывается; 204 |
| PUT / DELETE `/like` | Поставить / снять единственный лайк; 204 |
| GET `/comments?page=1&parentId=...` | Страница корневых комментариев или ответов указанного корня |
| POST `/comments` | `{text, parentId?}` → `{id}` |
| PATCH `/comments/{commentId}` | `{text}` — изменение своего комментария; 204 |
| DELETE `/comments/{commentId}` | Заглушка вместо текста; автор комментария или владелец цели; 204 |

GET не меняет состояние. Публичные цели доступны всем, приватные — владельцу либо
по действующей ссылке, переданной как `shareToken` в query каждого запроса.
Изменения требуют действующую сессию подтверждённого аккаунта и CSRF. Клиент не задаёт
actorId. Повторные установка лайка, снятие лайка и просмотр не увеличивают счётчики.

Комментарий содержит `id`, `author` (`id`, `displayName`, `username`), `text`, `parentId`,
`createdAt`, `updatedAt`, `isDeleted`, `canEdit`, `canDelete`. Текст после trim содержит
1–2000 символов и отображается как обычный текст. Ответ разрешён только на неудалённый
корень той же цели. Страницы по 20, порядок по времени создания и ID от старых к новым;
ответ содержит `items`, `total`, `page`, `pageSize`. Удалённые комментарии остаются
заглушками, текст становится null, ответы сохраняются. Редактирование удалённого
комментария запрещено. Собственные лайки и участие автора в обсуждении разрешены.

Недоступная цель — 404, чужое редактирование/удаление — 403, неверный текст/ответ/страница —
400. Конкурентные изменения и дубликаты при гонках — 409: повторить всю команду новым
запросом. Для POST комментария при неопределённом результате сети сначала перечитать
обсуждение, чтобы не создать повторный комментарий.

## Аватары, описание и подписки

`GET /api/auth/me` дополнительно возвращает nullable `bio` и `avatarUrl`.
`PATCH /api/auth/me/profile` принимает `displayName`, `username` и необязательное
`bio`: пропущенное поле сохраняет описание, null/пустая строка очищают. Текст после
trim ограничен 500 символами; переносы сохраняются, HTML не интерпретируется.

| Метод и путь | Контракт |
| --- | --- |
| PUT `/api/auth/me/avatar` | multipart: `file`, `cropX`, `cropY`, `cropSize`; 204 |
| DELETE `/api/auth/me/avatar` | Удалить аватар; 204, в том числе при его отсутствии |
| GET `/api/users/{id:guid}/avatar` | Изображение подтверждённого пользователя либо 404 |
| PUT `/api/users/{username}/follow` | Подписаться; повторная команда безопасна; 204 |
| DELETE `/api/users/{username}/follow` | Отписаться; отсутствие связи безопасно; 204 |
| GET `/api/users/{username}/followers?page=1` | Публичные подписчики |
| GET `/api/users/{username}/following?page=1` | Публичные подписки |

Все изменения требуют действующую сессию подтверждённого аккаунта и CSRF.
Подписка на себя — 400, отсутствующий/неподтверждённый пользователь — 404.
Конкурентные изменения — 409; повтор выполняется целиком новым запросом.

Аватар: один файл JPEG/PNG до 5 МБ; действуют существующие ограничения изображений
(8192 пикселя на сторону, 25 Мп, без анимации). Координаты — целые неотрицательные
пиксели после EXIF-ориентации; `cropSize` положителен, весь квадрат должен лежать
внутри изображения. Сервер повторно проверяет файл и обрезку, перекодирует результат
в PNG 512×512 без исходных метаданных. Неверная обрезка/данные — 400, большой файл —
413, неподдерживаемый формат — 415. Ответ изображения использует `Cache-Control:
no-store` и `X-Content-Type-Options: nosniff`; отсутствие аватара отображается
клиентом как инициалы.

`GET /api/users/{username}` сохраняет прежние поля и добавляет `bio`, `avatarUrl`,
`followersCount`, `followingCount`, `isFollowing`, `canFollow`. Гостю оба признака
доступных действий false; себе подписаться нельзя. Списки по 20, сортировка по
username и ID, оболочка `items`, `total`, `page`, `pageSize`. Только подтверждённые
профили, без email. Краткие представления людей и авторов комментариев содержат
nullable `avatarUrl`; представления вещей и образов — `ownerAvatarUrl` (при отсутствии
изображения этот URL возвращает 404). Ключ файла не раскрывается.

## Избранное, копирование и черновики

Все маршруты требуют действующую сессию подтверждённого аккаунта, изменения — CSRF.
OwnerId/actorId из клиента не принимаются. Уникальность и версии защищены БД;
конфликт — 409, недоступный ресурс или чужой черновик — 404, неверные поля — 400.

| Метод и путь | Назначение |
| --- | --- |
| GET `/api/favorites?kind=outfits&page=1` | Личное избранное, kind: items/outfits, страницы по 20 |
| GET `/api/{items|outfits}/{id}/favorite` | `{isFavorite}` для доступной цели |
| PUT / DELETE `/api/{items|outfits}/{id}/favorite` | Добавить / убрать, повтор безопасен; 204 |
| POST `/api/outfits/{id}/copies` | `{operationId}` (непустой UUID) → `{id}` копии |
| GET `/api/drafts?page=1` | Активные черновики, страницы по 20 |
| GET `/api/drafts/active?kind=items&targetId=...` | `{draft}` или `{draft:null}`; targetId пропущен для создания |
| GET `/api/drafts/{id}` | Личный черновик и результат его завершения |
| PUT `/api/drafts/{id}` | Создать/обновить черновик по клиентскому UUID |
| DELETE `/api/drafts/{id}?version=...` | Удалить активный черновик и его фото; 204 |
| PUT / DELETE `/api/drafts/{id}/photo?version=...` | Загрузить/удалить фото; возвращает обновлённый черновик |
| GET `/api/drafts/{id}/photo` | Фото только для владельца, no-store |
| POST `/api/drafts/{id}/save` | `{version}` → `{id}` сохранённого ресурса |

Для чтения статуса избранного, его добавления и копирования по приватной ссылке
передавайте `shareToken` в query. Избранное сортируется от новых к старым, затем по
ID. Элемент содержит targetId, kind, available, name, photoUrl, route. Если доступ
потерян, последние три поля null; запись можно удалить без доступа к цели. Личная
route может содержать действующую сохранённую ссылку; публичные DTO её не получают.

Копирование работает для собственных, опубликованных и доступных по ссылке образов,
включая их приватные вещи в контексте образа. Имя — «Название (копия)», все записи
приватны. Локальные фото копируются в независимые файлы, внешние адреса сохраняются.
Повтор одного operationId возвращает прежний результат даже после удаления источника;
новый осознанный запрос копирования использует новый operationId.

PUT черновика принимает kind, targetId (nullable), version (null при создании),
baseVersion и content. Content: name, description, category (nullable), color, size,
brand, photoUrl, photoMode (file/url), removePhoto, itemIds. Поля могут быть неполными;
полная доменная валидация выполняется при save. Сериализованные данные до 65536
символов, состав до 1000 ID. Ответ: id, kind, targetId, version, baseVersion,
updatedAtUtc, content, photoUrl, completedId. Ключи файлов не раскрываются.

Личные детальные представления вещей/образов содержат editVersion — непрозрачную
версию основы для baseVersion. Если исходные данные изменились, save даёт 409;
после сверки нужно обновить baseVersion актуальным editVersion. При удалённой цели
черновик доступен для просмотра/удаления, сохранение не создаёт замену автоматически.

Фото: один multipart file, JPEG/PNG до 5 МБ, существующие ограничения декодера.
Поля/фото черновика не меняют ресурс. Явный save атомарно применяет данные и состав,
передаёт фото ресурсу и завершает черновик. При ошибке данные и файлы сохраняются
для повтора; созданные только проигравшей командой файлы очищаются. Повтор успешного
save возвращает тот же id. Завершённые записи не входят в список активных.
